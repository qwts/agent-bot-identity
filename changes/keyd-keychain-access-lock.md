- keyd's Keychain items are now locked to keyd's own code, so another process running as you can no longer quietly stand in for one (#753).
  - keyd creates every item itself, through `SecKeychainItemCreateFromContent`, with an access whose every entry names its own code signature; the framework's default access trusted *any* application to write the value. It also turns keychain prompts off, so a call it is not entitled to fails instead of putting a dialog in front of you.
  - keyd checks an item's access list on every read. An App key it does not control is re-made in place with the same value, so an owner's imported key survives the upgrade untouched; anything under service `agent-bot.keyd` — the daemon grant-key pin, the presence seed and the owner's statement keys — is refused instead, because those values are what agent-bot trusts and any process in the account could already have written them. Refusing costs a one-time owner action: `owner/pin` re-pins the daemon key under one Touch ID prompt, removing keyd's `presence-key` item lets it make a fresh seed (a new presence key, so `keyd/presence.pub` has to go too and be pinned again), and removing `owner-pins` returns the owner's keys to "never approved" for `owner enroll` to record again.
  - `agent-bot` re-derives keyd's presence key from the code-signed binary on every owner action rather than trusting `keyd/presence.pub`, a file anything running as you can write. A cache the binary disagrees with is refused with `presence-pin-mismatch`, receipted, and left in place; remove `presence.pub` to pin again.
  - Still limited, and documented as such: an access list cannot stop a same-user process from planting an item before keyd first creates one, and the legacy file keychain does not gate every operation on one, so such a process can still blank or delete an item it cannot read. The durable fix is the data-protection keychain under a `keychain-access-groups` entitlement, which only the signed GeniusBar build can carry.
